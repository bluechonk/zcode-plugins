# run-trace

让长跑命令始终可观测：**边跑边看得到进度，边跑边落盘，死了能追溯**。

解决的是一个很具体的故障：agent 写了 `python train.py 2>&1 | grep -E '"event"'`，然后你什么输出都看不到，也不知道它是卡住了、跑完了、还是崩了。

## 这个写法到底哪里错了

不是「用了 grep」的错，是三件事叠加。以下全部实测（2026-11-24，本机 python 3.11 + Git Bash）：

| 现象 | 实测 |
| --- | --- |
| 输出攒到最后才出现 | 4 行输出、每行间隔 2 秒，经 `\| grep` 写入文件后轮询：**前 7 秒 0 行，第 8 秒一次性 4 行** |
| 崩溃被当成成功 | 崩溃脚本真实退出码 **3**，经 `2>&1 \| grep` 后 `$?` 变成 **0** |
| 报错内容消失 | 同一条命令，stderr 里的 `FATAL: cuda out of memory` 在管道后**完全不见** |

机制：`grep` 在非 tty 下按块缓冲（4KB 或 EOF 才吐）；管道的 `$?` 是最后一段的退出码；`2>&1` 把 stderr 并进 stdout，被 grep 过滤后就没了。

所以问题不在「筛选」，在于**筛选之前没有先落盘、也没有保住退出码**。

## 两个组件

### 1. `hooks/trace.mjs` —— 运行器

```bash
node "<插件根>/hooks/trace.mjs" [--log <路径>] [--timeout <秒>] [--echo-rate <行/秒>] -- <命令…>
```

同时做四件 shell 拼不出来的事：

- 终端**回显**（不加前缀，人看着就是命令本来的输出）
- **逐行**追加写日志并盖时间戳——边跑边写，不是跑完才写
- **透传真实退出码**，超时返回 124
- 结尾写 `# RESULT: success|failure|timeout`

关键设计：**日志里没有 `# RESULT:` 那行，就说明进程被杀了**。这是「它到底跑完了没有」的唯一可靠凭证。

**输出量大的命令加 `--echo-rate 20`**：终端每秒只回显 20 行，超出部分合并成一句「已省略 N 行」，**日志仍是全量**。压缩的只是给人看的实时流，不是事后追溯的现场。默认不限速——多数命令输出不大，限速反而让人以为卡住了。

**跨 shell**：在 Windows 上自动用 Git Bash 执行（而不是 Node 默认的 cmd.exe），所以 `.venv/Scripts/python.exe` 这类 POSIX 路径、`&&` 链、单引号都与调用方一致。找不到 Git Bash 时会明确警告，不静默换 shell。

**超时真的能停住**：`killTree` 会杀掉整棵进程树。只杀直接子进程（那个 shell）时，真正的负载会变成孤儿继续跑并占着 stdout，`close` 永不触发——超时保护形同虚设（这是实测踩出来的 bug）。

### 2. 四个 hook —— 规范 + 时机 + 复查

| 事件 | 检测 / 注入 | 命中后 |
| --- | --- | --- |
| `SessionStart` | 长跑可观测性规范卡 | 注入（含「Agent 能看到的 = 人能看到的」这句核心） |
| `UserPromptSubmit` | 规范重申，每 12 轮一次、首轮必说 | 注入 |
| `PreToolUse`（Bash） | 长跑 + 管道过滤 + 无落盘 | 提示 `tee \| grep --line-buffered` 改法 |
| `PreToolUse`（Bash） | 长跑但完全没落盘 | 提示加 `tee` 或改用 trace |
| `PreToolUse`（Bash） | 管道最后一段是过滤器 | 提示 `$?` 会被覆盖，给出 `pipefail` 改法 |
| `PreToolUse`（Bash） | `2> /dev/null` 且长跑 | 提示报错会消失 |
| `PostToolUse`（Write/Edit） | Python 多处 `print` 但没 flush | 提示加 `flush=True` 或 `-u` |

长跑判定覆盖 Git Bash 与 PowerShell 两侧：`python` / `node` / `npm` / `pytest` / `uv sync` / `dotnet` / `docker build` / `git clone` / `pwsh -File` / `powershell -File` / `Start-Process` 等。

**为什么两条路都走**：规范卡管「决定怎么跑之前」的判断，hook 管「敲下命令那一刻」的拦截。只靠提示词模型会忘，只靠 hook 覆盖不了规划阶段——用户的原话是「尽量都走」。

全部只提示不 deny：长跑不带 tee 有正当场景（马上重跑、只关心末尾），硬拦会逼模型把命令拆坏。

## 为什么不做成「自动改写命令」

想过，放弃。自动给命令套 `tee` 会改变语义：用户的重定向意图被覆盖、`$?` 的含义变了、日志路径冲突。**提示 + 现成改法**让模型自己判断，比替它改安全。

## 与同类方案的区别

`| tee` 是最常见的答案，它解决「落盘」，但**不解决**：

- 每行没有时间戳 → 分不清卡住还是慢
- `tee` 之后 `$?` 仍是下游的 → 崩溃看不出来
- 没有结束标记 → 分不清跑完还是被杀

trace 补的正是这三块。它不替代 `tee`，是把它做不到的部分做完。

## 验证

测试在 `tests/` 下，两套共 **190 条断言**：

```bash
node tests/run.mjs            # 两套都跑
node tests/run.mjs core       # 只跑核心行为（56 条）
node tests/run.mjs boundary   # 只跑边界与回归（134 条）
```

用例由 LongCat-2.5 分六个维度设计、再逐条实测固化：长跑命令识别、前缀与包装器、输出处理与日志格式、检测规则边界、hook 协议健壮性、真实开发场景。

**每个维度的用例都先在 `.tmp/probe-*.mjs` 里对真实实现跑过一遍**，确认现象后才写成断言——所以下面这些不是设想，是实测结论。

### 已知盲区（14 条，用例已锁定现状）

长跑识别的段首锚点吃不到命令前缀，这些写法**当前不会提示**：`time` / `stdbuf` / `xvfb-run` / `watch` / `find -exec` / `xargs` / `sudo` / `nice` / `nohup` / `env` / 环境变量赋值 / Windows 盘符路径 / `~/` 家目录 / 引号包裹的绝对路径。

这些用例断言的是「现在确实静默」。哪天修好了，测试会失败并提示反转断言——这是刻意的：让盲区不会被悄悄忘记。

### 修复记录

跑测试时抓出并已修的四个 bug：孙进程持有管道导致 trace 挂起、`--log` 指向目录时子进程成孤儿、注释里的 `flush=True` 误豁免、语句链被当成整体判。

- 五类检测规则的正例与反例（含短命令不误报、同命令去重）
- trace 的成功 / 崩溃 / 超时三种收尾，退出码与 `RESULT` 标记
- **边跑边写**：跑到 2.5 秒时文件里已有输出、且还没有结束标记
- **强杀**：`kill -9` 后已有内容保留、无 `RESULT` 标记
- **回显节流**：300 行输出经 `--echo-rate 10` 后终端被压缩、日志仍是全量 300 行、有省略提示；不限速时终端全量
- **跨 shell**：`pwsh -File` / `powershell -File` / `dotnet build` / `uv sync` / `git clone` 都识别为长跑
- **提示注入**：SessionStart 规范卡内容、UserPromptSubmit 首轮必说 + 2-11 轮节流
- **关键回归**：同一条崩溃命令，shell 管道退出码 0，trace 退出码 7

写测试时踩到四个真 bug，都修了：

1. `2>&1` 被重定向判定误当成「已落盘」，导致最关键的那条提示不触发；
2. `missingFlush` 门槛设成 3 处 `print`，漏掉「循环里一条进度 + 结尾一条结果」这个最典型形态；
3. 超时只杀 shell 不杀进程树，python 成孤儿占着管道，`close` 永不触发，日志没有 `END` / `RESULT`；
4. 节流的省略提示只在跨秒窗口时补报，单秒内刷完的输出永远等不到下一窗口。

## 实战：一次真实的「看不见」故障

起因是一条命令：

```bash
cd python && .venv/Scripts/python.exe ../.tmp/probe_call_overhead.py 2>&1 | grep -E '"event"'
```

跑完什么也没有。逐层排查后确认了四件事，全部可复现：

1. **`| grep` 在非 tty 下按块缓冲**：4 行输出、每行间隔 2 秒，写进文件后轮询——前 7 秒 0 行，第 8 秒一次性 4 行。
2. **退出码被吞**：崩溃脚本真实退出码 3，经 `2>&1 | grep` 后 `$?` 变成 0。Agent 会认为「跑成功了」。
3. **stderr 消失**：同一条命令，`FATAL: cuda out of memory` 在管道后完全不见。
4. **脚本本身没 flush**：即使去掉 grep，Python 在管道下默认块缓冲，`print` 也要等结束才出。

于是用户看到的是「没有任何输出」，Agent 的上下文里也是空的——它只能猜，或者编。

换成 trace 之后：

```
[20:50:36.776] {"event": "corpus", "n": 2048}
# [20:53:22.600] TIMEOUT 超过 180s，终止进程
# [20:53:22.925] END exit=1 用时 180.3s
# RESULT: timeout
```

进度看得见（第 14 秒就出现了第一行）、超时自动收尾、`RESULT` 标记明确说明没跑完。
